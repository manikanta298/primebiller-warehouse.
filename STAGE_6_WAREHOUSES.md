# Stage 6 — Godowns / Warehouses

**Review status: awaiting approval.** **Screen:** `/warehouses`. Continues approved Stage 5. Do not advance to Stage 7 until the user approves this stage.

## Screen delivered

- Existing **Warehouses** heading and three-column, bordered warehouse-card design retained, including name, code, type, address, stock valuation, default sales flag, negative-stock rule and manager.
- Warehouse search by code, name, location, manager or type; active/inactive status filter with a count and empty-result state.
- Original **New warehouse** and **Edit warehouse** forms retain code, name, type, manager, address, state, optional separate GSTIN, negative-stock toggle, sales-default toggle and active toggle. Added inline validation, Cancel, unsaved-change confirmation and persistent backend errors.
- **View stock** opens read-only item inventory for the selected warehouse: item/SKU/UOM, on-hand, held, free and value. The table loads through the existing org-scoped `/items` endpoint. **Quantities are not summed across SKUs with different units**; the card instead reports stocked SKU count and stock valuation.
- The dedicated stock window is read-only; stock is updated through receipts/GRNs, transfers and approved adjustments, not by editing warehouse master data.
- Both list and inventory query caches are organisation-scoped. When the selected organisation changes, open warehouse dialogs and search/filter state reset.

## API and database

- Uses existing `godowns`, `items` and `item_stock` MySQL tables; **no additional migration**. Existing Docker Compose services, frontend/backend Dockerfiles and SQL scripts are retained.
- `GET /api/v1/orgs/:orgId/godowns?detail=1` now returns stock valuation (2-decimal), stocked SKU count and held/on-hand metrics with a join checked for item/stock organisation identity. Empty warehouses receive zero-valued metrics.
- `POST /api/v1/orgs/:orgId/godowns` and `PUT /api/v1/orgs/:orgId/godowns/:id` require JWT + Owner/Manager role, require URL org to match the authenticated selected org and validate input through shared warehouse rules. No client-supplied ID is accepted on creation; edits check ID and organisation within the transaction.
- Trims/normalises code, name, address, manager and GSTIN; validates warehouse code syntax, field lengths, valid GST state, GSTIN checksum/state prefix, and rejects inactive sales defaults. Codes remain unique within an organisation.
- Deactivation is rejected when **any item** has nonzero on-hand (even if aggregate stock nets to zero) **or held reservations**; it is not enough for aggregated quantity to be zero.
- When designating a new default for sales, the transaction locks the organisation row so changes to the default are serialised, clears the prior default only within that organisation, then inserts/updates the chosen warehouse. Updates use an explicit `WHERE org_id=? AND id=?`; no cross-organisation upsert.
- React demo backend mirrors the same validation, organisation ownership and stock safety. Shared rules source is `src/lib/godown-rules.ts` and the server copy is regenerated by `node scripts/sync-shared.mjs`.

## Test / review steps

1. Run `cp .env.example .env`, update secrets/passwords, then `docker compose up -d --build`. Use existing README instructions for owner setup if this is a fresh database. Preserve `mysql_data` when updating.
2. Sign in as Owner/Manager and visit `http://localhost:8080/warehouses`. Check the original three-column desktop cards and stacked mobile cards. Search across location/manager/name and filter active/inactive.
3. Open **View stock** for each warehouse; verify only that warehouse's items appear, quantities use the item's base UOM, and free = on-hand − held. Check an empty warehouse too.
4. Edit/create a warehouse; try missing name, unknown state code, invalid or mismatched GSTIN, duplicate code, and inactive + default-for-sales. Verify Save stays disabled and the server also rejects invalid direct requests.
5. Try deactivating a warehouse with positive, negative or reserved stock. The API must reject it until balances are cleared using stock movements. Try changing the default for sales; only one active default should remain in the organisation.
6. Switch organisations; cards/stock dialogs must reset, and other-organisation IDs must be rejected by PUT even when typed manually. Verify read-only access for Storekeeper/Sales/Accountant roles and that unauthorised writes fail.
